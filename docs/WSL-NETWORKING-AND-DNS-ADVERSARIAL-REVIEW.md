# Adversarial Review: WSL Networking & DNS Topologies in Omarchy-WSL

**Distribution Engine:** Omarchy-WSL (Arch Linux for WSL2)
**Target Architectures:** ARM64 (`aarch64`, e.g. Snapdragon X) and x86_64
**Goal:** keep DNS, proxies, TLS trust, package downloads and container networking working across NAT and mirrored networking, corporate VPNs (GlobalProtect, AnyConnect, Zscaler), TLS-inspecting proxies and restrictive firewalls, without silently weakening the guest.

Section 7 describes what the repository actually ships; sections 2–6 are the analysis behind it. Statements about WSL and Windows behaviour come from Microsoft documentation and field reports; where we have not verified a behaviour ourselves we say so.

---

## 1. Threat Model & Topological Realities

```
+-------------------------------------------------------------------------+
|                              WINDOWS HOST                               |
|  +-------------------------------------------------------------------+  |
|  | Enterprise VPN client (GlobalProtect / AnyConnect / Zscaler)      |  |
|  | Windows Defender Firewall & Hyper-V firewall                      |  |
|  | WinINet proxy settings (static proxy / PAC URL)                   |  |
|  | Windows Root CA store (corporate PKI / TLS-inspection roots)      |  |
|  | Windows services (svchost, IIS, BranchCache, ports 53/80/443)     |  |
|  +-------------------------------------------------------------------+  |
|                                    ^                                    |
|                 Hyper-V switch / VFP (mirrored) / vsock                 |
|                                    v                                    |
|  +-------------------------------------------------------------------+  |
|  |                         OMARCHY-WSL GUEST                         |  |
|  |  glibc resolver <--- /etc/resolv.conf (generated by WSL)          |  |
|  |  pacman / curl / git <---> proxy, TLS trust, mirrorlist           |  |
|  |  dockerd / podman (netavark, pasta) <---> container bridges       |  |
|  |  default user (UID 1000) <---> local dev servers                  |  |
|  +-------------------------------------------------------------------+  |
+-------------------------------------------------------------------------+
```

In enterprise developer setups the guest network faces:
1. **VPN routing hijacks:** corporate VPNs claim the default route and drop traffic whose source address is not the VPN-assigned one (anti-spoofing).
2. **DNS interception & split horizon:** internal names resolve only through enterprise resolvers; public resolvers (1.1.1.1, 8.8.8.8) may be blocked or answer NXDOMAIN for internal zones; DNSSEC data may be stripped.
3. **TLS inspection:** proxies re-sign TLS with a corporate root that Arch's `ca-certificates` does not contain.
4. **ICMP black-holing:** ping is often dropped, which breaks ping-based mirror ranking.
5. **Port & subnet collisions:** host services clash with guest services, and container subnets collide with corporate address ranges.

## 2. Attack Angle 1: `networkingMode=mirrored` vs `NAT`

### 2.1 Comparison

| Property | `networkingMode=NAT` | `networkingMode=mirrored` (Windows 11 22H2+) | Failure mode |
| :--- | :--- | :--- | :--- |
| **Virtual switch** | Hyper-V internal switch; the guest gets a private address from a range Hyper-V picks | Guest mirrors the host's interfaces and addresses | NAT is isolated; mirrored shares the host stack |
| **IPv6** | Usually not routed | Dual-stack like the host | NAT guests often have no usable IPv6 |
| **VPN compatibility** | Traffic from the NAT subnet is often dropped once a VPN connects | Uses the host adapters, so traffic follows the VPN routes | Mirrored still obeys host firewall rules |
| **Windows firewall** | Largely bypassed | Hyper-V firewall applies to WSL traffic | `firewall=true` can block Linux traffic without any Linux-side log |
| **Port conflicts** | Linux `0.0.0.0:80` is separate from Windows | Same port space: a port Windows uses cannot be bound in Linux | IIS, BranchCache etc. cause `EADDRINUSE` |
| **Localhost** | Windows reaches guest ports through localhost forwarding | Shared loopback in both directions | See 2.2.4 for the dual-stack trap |

Mirrored networking needs Windows 11 22H2 or later; on older builds WSL does not offer it (exact behaviour when it is configured anyway varies by WSL version — not verified here).

### 2.2 Failure Analysis

#### 2.2.1 NAT behind a VPN
In NAT mode the guest sits behind Hyper-V's NAT. When the host connects to a VPN, the VPN client changes the Windows routing table and often enforces egress filtering; packets originating from the Hyper-V NAT subnet are then dropped or not routed into the tunnel. Typical result: the guest loses outbound connectivity as soon as the VPN connects. DNS tunneling (section 3) keeps name resolution working through the Windows DNS client, but TCP traffic still has to get through the NAT.

#### 2.2.2 Mirrored mode and the Hyper-V firewall
With mirrored networking the Hyper-V firewall filters guest traffic. Enterprise policies that block outbound traffic not matching an approved rule can drop guest connections, and nothing about the drop is visible in the Linux kernel log.

#### 2.2.3 Port collisions on `0.0.0.0`
Mirrored mode shares the port space: if a Windows service already listens on `0.0.0.0:80`, a Linux web server binding the same port gets `EADDRINUSE`.

#### 2.2.4 Dual-stack localhost
A dev server bound only to `127.0.0.1` is unreachable for a client that resolves `localhost` to `::1` first (most Windows browsers). Bind to both (`0.0.0.0` and `::`, or `localhost` with dual-stack support). Note: the `.wslconfig` key `hostAddressLoopback` is unrelated — in mirrored mode it lets the host and the guest reach each other through an IP address assigned to the host (Microsoft wsl-config documentation); it does not change `localhost` resolution.

## 3. Attack Angle 2: `dnsTunneling`, `autoProxy` and the resolver

### 3.1 Who owns `/etc/resolv.conf`

```
[ WSL instance start ]
  ├── generateResolvConf = true (Omarchy-WSL default):
  │     WSL writes /etc/resolv.conf at every start:
  │       dnsTunneling=true  -> nameserver 10.255.255.254 (WSL's DNS proxy, answers via
  │                             the Windows DNS client, so VPN/split-horizon rules apply)
  │       otherwise          -> the NAT gateway (WSL's DNS proxy) or the host's resolvers
  │
  └── generateResolvConf = false:
        WSL leaves /etc/resolv.conf alone; something else must provide it.

[ systemd-resolved ]
  ├── serves 127.0.0.53 and expects uplink servers from networkd / NetworkManager / DHCP
  └── WSL's eth0 runs no DHCP client, so resolved has no uplink unless configured by hand
```

### 3.2 Conflicts

#### 3.2.1 `dnsTunneling=true` plus default `systemd-resolved`
If resolved is enabled and `/etc/resolv.conf` points at its stub (127.0.0.53), applications ask resolved, which has no upstream server: every lookup fails. If WSL also writes `/etc/resolv.conf`, two components fight over one file and resolution flaps. Omarchy-WSL avoids this by masking resolved (section 7).

#### 3.2.2 DNSSEC on enterprise networks
`systemd-resolved` defaults to `DNSSEC=allow-downgrade`. DNS firewalls and corporate resolvers that rewrite or strip records can make validation fail, which resolved reports as SERVFAIL.

#### 3.2.3 mDNS and LLMNR in mirrored mode
In mirrored mode Linux shares the host's ports; Windows already uses UDP 5353 (mDNS) and 5355 (LLMNR). resolved's defaults for both would compete with the host.

#### 3.2.4 `autoProxy=true` and TLS inspection
`autoProxy=true` hands the Windows proxy to WSL sessions. Behind a TLS-inspecting proxy, `pacman`, `curl` and `git` then fail certificate verification until the corporate root is trusted in Linux:
```
error: failed retrieving file ... SSL certificate problem: self-signed certificate in certificate chain
```

## 4. Attack Angle 3: Container Engines (Docker & Podman)

```
+-------------------------------------------------------------------------+
| OMARCHY-WSL KERNEL                                                      |
|  Host-facing interfaces: eth0 (NAT) or the mirrored host adapters       |
|  Container bridges:      docker0 (Docker's default bridge subnet)       |
|                          podman0 (10.88.0.0/16 by default)              |
+-------------------------------------------------------------------------+
```

#### 4.1 Subnet collisions
Docker's default bridge subnet and its default address pools are taken from the RFC1918 ranges that corporate networks and VPNs also use. When a container network overlaps a corporate or VPN route, the kernel delivers that traffic to the local bridge: the corresponding intranet hosts (or, in NAT mode, the WSL gateway) become unreachable.

#### 4.2 iptables rules and exposure
`dockerd` installs NAT rules (`POSTROUTING -s <bridge subnet> ! -o docker0 -j MASQUERADE`). Published ports (`-p 8080:8080`) bind `0.0.0.0`; in mirrored mode that is the host's LAN address, which may violate policy.

#### 4.3 Rootless Podman and pasta
Rootless Podman uses `pasta`, which copies the guest's default route and addresses. With unusual routing (VPN policy routes, mirrored adapters) pasta may fail to find a default route and refuse to start the container.

## 5. Attack Angle 4: pacman Mirrors Behind Firewalls

#### 5.1 Ping-based ranking
Mirror rankers that measure latency with ICMP fail where ping is dropped; a ranker that then writes its (empty) result to `/etc/pacman.d/mirrorlist` leaves pacman with `no servers configured for repository`.

#### 5.2 Dead mirrors
pacman's built-in downloader uses a 10 s connect timeout and aborts stalled transfers (low-speed limit; `--disable-download-timeout` turns that off), then moves on to the next `Server` line. A black-holed mirror therefore costs seconds, not minutes, and no `XferCommand` is needed.

## 6. Attack Angle 5: Ports and Windows Interop

#### 6.1 Privileged ports
Ports below 1024 need root or `CAP_NET_BIND_SERVICE`. Lowering `net.ipv4.ip_unprivileged_port_start` to 0 removes that for every local user and service: any process could take 22, 53 or 443 before the real service does, and in mirrored mode such a port is reachable on the host's LAN address. Omarchy-WSL keeps the kernel default (1024) and documents the opt-ins: `setcap cap_net_bind_service=+ep <binary>`, a reverse proxy, or a deliberate `sysctl net.ipv4.ip_unprivileged_port_start=80`.

#### 6.2 Windows `%PATH%`
WSL appends the Windows `%PATH%` by default. That puts hundreds of Windows directories (slow DrvFs lookups, colliding names such as `find.exe`, `sort.exe`, `bash.exe`) behind every command lookup. Omarchy-WSL sets `appendWindowsPath = false`; the Windows tools it needs are resolved by absolute path, and `wsl/bin/wsl-shims-setup.sh` (run as root at runtime) links a curated set into `/usr/lib/omarchy-wsl/bin`.

## 7. What Omarchy-WSL Ships

```
+-----------------------------------------------------------------------------+
| 1. HOST: tools/generate-wslconfig.ps1                                       |
|    Windows 11: networkingMode=mirrored, dnsTunneling, autoProxy, firewall;  |
|    [experimental] hostAddressLoopback, ignoredPorts; NAT on older builds    |
|    (-ForceNAT). Merges into an existing .wslconfig.                         |
|                                                                             |
| 2. GUEST KERNEL: wsl/sysctl.d/99-zz-omarchy-wsl-network.conf                |
|    rp_filter=2 (loose) for VPN multi-homing; privileged ports stay at 1024; |
|    route_localnet and IPv6 forwarding off; no ip_forward (dockerd and       |
|    netavark enable it when they create a bridge); keepalives, backlogs.     |
|                                                                             |
| 3. DNS: one model                                                           |
|    wsl.conf generateResolvConf = true: WSL writes /etc/resolv.conf.         |
|    systemd-resolved, -networkd, -timesyncd are masked in the image.         |
|    omarchy-dns-sync (omarchy-dns-sync.service, TimeoutStartSec=10s, not     |
|    ordered before network-online.target): keeps a healthy file untouched    |
|    and records it as last-known-good; repairs a missing/empty one from      |
|    last-known-good, Windows DNS servers (6 s PowerShell probe) or the       |
|    gateway; validates every nameserver/search token; never adds public      |
|    resolvers unless --public-fallback; no `options rotate`.                 |
|    The resolved drop-in is installed but dormant (opt-in instructions in    |
|    its header).                                                             |
|                                                                             |
| 4. PROXY & CA TRUST (omarchy-proxy-sync.service, TimeoutStartSec=10s)       |
|    omarchy-ca-sync: LocalMachine\Root certificates Linux does not trust     |
|    yet (SHA-256 compare), minus the Windows Disallowed stores; optional     |
|    CurrentUser\Root and --thumbprint allowlist; managed anchors pruned when |
|    they leave Windows; a failed query changes nothing.                      |
|    omarchy-proxy-sync: WinINet ProxyServer/ProxyOverride validated against |
|    a strict host:port grammar (hostile values rejected, exit 3), written    |
|    single-quoted to /etc/environment.d and /etc/profile.d. PAC scripts are  |
|    reported, not evaluated.                                                 |
|                                                                             |
| 5. PACMAN                                                                   |
|    Download sandbox on (DownloadUser = alpm), built-in downloader timeouts. |
|    omarchy-mirror-sync: HTTPS-only HEAD probes (3 s connect / 5 s total),   |
|    Omarchy's stable mirror pinned first when reachable, never writes a list |
|    without a valid https Server line, keeps mirrorlist.bak.                 |
|                                                                             |
| 6. CONTAINERS: wsl/docker/daemon.json, wsl/podman/containers.conf           |
|    Docker: bridge + pools in 198.18.0.0/16 (RFC 2544 benchmark space), MTU  |
|    1420, no hard-coded DNS (containers inherit WSL's resolv.conf).          |
|    Podman: 198.19.0.0/16, pasta MTU 1420, ports published only with -p.     |
|                                                                             |
| 7. DIAGNOSTICS: omarchy-netdoctor                                           |
|    Audit (PASS/WARN/FAIL counted, INFO not) and --repair, which runs the    |
|    four sync tools (as root) and audits again.                              |
+-----------------------------------------------------------------------------+
```

Limits that remain: PAC-only proxies need manual configuration; containers on a user-defined Docker network use Docker's embedded resolver, which forwards to the resolvers in `/etc/resolv.conf` (if a corporate setup needs something else, set `"dns"` in `daemon.json` explicitly); none of this can bypass a host firewall or VPN policy that deliberately blocks WSL traffic. Behaviour is covered by `tests/test_network_sync.sh` and `tests/test_networking_adversarial.sh`; nothing in those suites runs against a real Windows host.
